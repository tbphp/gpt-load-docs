# GPT-Load 广告合作管理

## 范围与持久记录

- 本 Skill 仅安装于 gpt-load-docs 的 `.agents/skills/`，不安装到全局或 gpt-load 项目。
- 从当前官网仓库启动；涉及 README 或渠道权益时，可处理关联的 gpt-load 仓库，但先定位仓库、读取其规则并保留已有改动。作者本机参考位置为 `/Users/tbphp/www/gpt-load`，不存在时询问位置，不猜测其他仓库。
- 通用套餐见 [references/packages.md](references/packages.md)，接入或报价时读取。每笔合作记录见 [references/cooperation-record.md](references/cooperation-record.md)，新增或更新记录时读取。
- 合作记录存于官网主检出的 `docs/sponsorships/<brand-slug>.md`，不存于临时 Worktree；用 `git worktree list` 定位。首次写入前确认该目录被 Git 忽略且未被跟踪。记录与 Skill 分离，不强制加入 Git，不写入用户全局记忆。
- 一笔合作一个稳定标识；先检索同品牌记录及现有展示，避免重复接入和重复提醒。仅从当前用户确认、记录、代码及上线证据恢复事实，不将报价稿视为已付款或已上线。
- 创建 Skill 本身不创建真实订单或提醒；没有实际合作资料时不建立虚构记录。

## 新增接入

1. 确认套餐与加购，列出权益及所需席位；按套餐表检查组合是否合法。核对在约记录和实际展示，精选最多 3 席、首席唯一；无法从代码判断是否已被预订时询问用户，不默认空缺或挤掉已有合作方。
2. 一次收集仍缺少的必要物料，复用用户已给出的内容：
   - 所有套餐：品牌名称、一个推广链接、Logo、中文介绍及核心卖点。约 150 字、3–5 个卖点是物料建议，已有原稿足够展示时不要求为凑数量补资料。
   - 商务联系人默认不收集。用户明确不需要提供的字段可忽略，记录为“不收集”，不反复追问或列为上线阻塞项；不要将某个字段的豁免扩大到付款、周期、席位或必要的技术验证资料。
   - 渠道合作或首席套餐另需：API 文档、Base URL、支持协议和模型列表、测试账号或 API Key、足够测试额度、技术联系人。基础＋精选不要求这些资料，也不增加渠道预设。
   - 合作信息：购买周期、优惠、赠送天数、付款状态、期望上线日期、链接 `rel` 约定。周期或付款尚未确定时，继续物料整理和预览，不假装已经满足上线条件。
3. 给出订单摘要。套餐价、折扣、赠送天数分别计算；“两个季付”等歧义影响金额与期限时先确认。优惠只应用于用户明确指定的订单，不默认每单九折或赠送 15 天。
4. 制作最小接入改动：优先保留合作方提供的各语言原文，补齐缺失语言、复用现有布局，按套餐落实展示顺序。所有套餐覆盖三语 README；精选和首席才包含官网赞助位。涉及渠道权益时检查当前接入方式，完成现有协议的兼容性与稳定性验证；定制开发另行确认。
   - 官网当前入口线索：`src/app/(v2)/page.tsx`、`src/app/(v2)/sponsor/page.tsx`、`src/i18n/v2/dict/{zh,en,ja}.ts`。先重新读取，路径和结构可能变化。
   - gpt-load 的三个 README 先实际定位并读取，保持同一赞助内容和权益顺序。
   - 旧版展示不默认同步新增；已约定覆盖时再修改。不要把某个历史套餐或展示位置自动套给新广告。
5. 完成匹配改动范围的检查，并给用户看实际文案、展示预览和差异；素材里的宣传主张不能当成已经验证的事实。公开内容不包含报价、付款详情和联系人。套餐不保证流量、转化或产品背书，也不改变调度权重。
6. 按双方确认的内容和付款状态推进上线。遵守各仓库当前提交、推送、PR 和发布规则；已有明确授权不重复询问。修改完成或合并不等于上线，核验真实 README 和官网展示、图片、跳转、三语及移动端。不同权益不同步上线时记录各自状态，与用户明确共同计费起点。
7. 记录实际上线日、明确的到期日和验收证据，再设置到期提醒。用户明确指定计费日期时按其约定；否则自正式上线日起算。不要以提交日或预期发布日期代替正式上线日。

## 文案与素材差异确认

- 逐一对照合作方原稿、三语 README、官网首页和赞助页；标题、正文、按钮文字和推广链接均须核对，不只检查正文。
- 任何改写、缩写、删减、标点变化、页面间内容差异及新增翻译，都向用户列明位置、语言、原文、拟用文字和调整原因；Logo 的裁切、留白及颜色等调整也须披露。HTML 转义等不改变显示文字或实际链接的编码处理可合并说明。
- 可以先制作本地候选稿和预览；所有与合作方原稿不一致的内容须得到用户明确确认后才可发布。不得仅用“已精简”“已翻译”“复用布局”代替差异说明，不把确认付款、上线日期或席位视为确认文案。
- 合作记录保存差异清单及对应确认依据；尚未确认的候选稿明确标记，已确认内容不重复询问，后续有新调整时只确认新增差异。

## 链接标记

- 新订单收集 `rel` 约定；付费链接默认建议 `sponsored noopener noreferrer`，`nofollow` 可作为 `sponsored` 的替代。
- 若广告商要求仅 `noopener noreferrer`，简短说明这两项不标记付费关系、存在 Google 搜索政策风险。用户已知情并明确选择后，记录并按该订单执行，不反复劝阻，也不影响其他广告的标记。
- 不把“广告商接受某属性”推断为用户已授权删除现有广告标记。链接属性不影响套餐权益或付款状态；推广链接中的追踪参数按约定保留。

## 到期后一天提醒

- 唯一默认通知时间：到期后的第一个自然日，`Asia/Shanghai` 上午 09:00；用户可另指定时间。不设提前 7 天或到期当天提醒，不自动下架。
- 先确定具体到期日；按自然月计算月付、季度按 3 个自然月，赠送天数另加。月底及到期日是否含当日有歧义时，将明确起止日期给用户确认，不能默认为季度等于 90 天。计算记录保留约定口径。
- 通过 Codex 内置 `automation_update` 工具创建或更新当前任务的 heartbeat；调用前发现工具、读取当前 schema。先查询记录中的 automation id，必要时只读检查 `$CODEX_HOME/automations/*/automation.toml`，避免重复创建。
- 优先使用工具当前支持的精确日期安排。如果仅支持周期 heartbeat，设每天本地 09:00 检查：通知日前保持安静；到期后一天首次运行时读取最新记录，确认仍未续费、未下架且尚未提醒，才通知用户并记录已提醒；随后用工具暂停自身，防止每天重复提醒。提醒日错过则下一次运行补发一次，不重新推算周期。
- 自动化 prompt 必须包含主检出记录绝对路径、合作标识、automation id 的查询方式、时区和通知日，并要求始终以最新记录为准。不得写入 API Key；不得自动修改广告、联系广告商或发送邮件。无可执行日程或工具失败时如实记录失败，不声称提醒已设置，不用操作系统 cron 绕过。
- 保存工具返回的 automation id、实际日程和状态；确认工具成功后才报告已设置。使用用户可读日期，不向用户输出原始 RRULE。

## 修改与续费

- 修改广告时只更新指定内容及对应语言和位置，保留未改变的合作权益和期限。
- 续费确认新周期、优惠和赠送天数；默认从原合作结束处连续续接。已中断合作或用户另有日期要求时明确新起止日期，不能一律从今天起算。
- 更新同一合作记录并保留历史摘要；更新或恢复已有提醒，不创建重复提醒。撤下中的广告若要恢复，重新核验物料、席位和上线状态。

## 下架

1. 按合作记录与当前代码定位该品牌全部已接入位置，给出具体范围；明确的下架指令已授权移除广告展示，不重复请求同一授权。
2. 移除对应 README、官网及约定的商业展示标识，调整剩余展示，保持其他赞助商不变。仅删除确认无引用的专属素材。
3. 渠道预设的删除或停用可能影响已有用户：先核对影响，得到针对该行为的明确选择后处理；不能将撤广告等同于删除渠道、凭据或用户配置。
4. 按各仓库规则完成验证与交付；未上线前记录为“下架待发布”，不得声称已撤下。停用该合作提醒并记录结果；保存合作历史，实际线上撤下后记录下架时间及证据。

## 交付说明

简洁说明当前合作权益、已完成步骤、实际验证、仍缺资料或待发布内容，以及提醒是否真正设置成功。不要为单纯咨询创建记录、代码改动或自动化。
